Fix before the next build 6 items

F1Drop android:persistent="true" from the relay app

On this tablet a persistent system app that crashes during boot sends the device into a recovery loop. That happened on 2026-11-02 with Lenovo's own persistent tbengine. The relay does not need it: service.sh and the boot receiver already start the foreground service.

Fix

Set persistent="false" or remove the attribute. Our test build already runs this way.

F2service.sh restarts Bluetooth on the first boot

The first time pm enable/pm disable changes a Bluetooth component's state, PackageManager kills the owning app. On boot 1 this hit 12 s after boot_completed and the stack restarted three services:

ActivityManager: Killing 1925:com.android.bluetooth/1002 (adj -700): change com.android.bluetooth
am_kill : [0,1925,com.android.bluetooth,-700,change com.android.bluetooth]

The trigger was the first-time state change on avrcpcontroller.AvrcpControllerService (enable) and avrcp.AvrcpTargetService (disable). Boot 2 was clean because the calls no longer change anything.

Fix

Apply the component states once at install time, while the system is up, and keep the boot-time calls as no-ops. Also drop the AvrcpTargetService disable: its manifest gate profile_supported_avrcp_target (0x7f02000c) is already false on this build, so the call only adds a state change.

# customize.sh
if $BOOTMODE; then
  for c in a2dpsink.A2dpSinkService avrcpcontroller.AvrcpControllerService \
           avrcpcontroller.BluetoothMediaBrowserService hfpclient.HeadsetClientService \
           pbapclient.PbapClientService pbapclient.AuthenticationService; do
    pm enable --user 0 com.android.bluetooth/.$c
  done
fi

F3Removing the module does not undo everything

The README says removal undoes everything, and the module has no uninstall.sh. These outlive the module:

  • Component states set with pm (saved in package-restrictions).
  • settings global hidden_api_policy = 1.
  • The deviceidle whitelist entry and /data/adb/carrelay.
  • Connection policies written by Pin roles (kept in the Bluetooth database per device).
Fix

Record the prior state of each component and setting at install, and restore exactly that. Magisk runs uninstall.sh early in boot when pm and settings are not available yet, so have it drop a one-shot /data/adb/service.d/carrelay_cleanup.sh that reverts after boot and deletes itself. Do not blanket-reset the sink services: on this tablet A2dpSinkService, HeadsetClientService, PbapClientService, AuthenticationService and BluetoothMediaBrowserService were already enabled by our own setup and must stay enabled.

F4Do not relax hidden_api_policy globally

service.sh and SystemBootstrap set hidden_api_policy 1, which turns hidden-API enforcement off for every app on the device and survives removal. The relay is a /system/priv-app with usesNonSdkApi="true", so it is already exempt, as your own comment says.

Fix

Remove both settings put global hidden_api_policy 1 calls.

F5Overlay handling logs failures for overlays that are active

Both overlays are static, so cmd overlay enable and set-priority cannot act on them. The boot log reports a failure although both are enabled and the lookups return the overlaid values:

[CarRelay-svc] com.local.btsink.overlay not present (ok)
[CarRelay-svc] com.carivi.bt.overlay enable failed/not present
[CarRelay-svc] bool/a2dp_sink_automatically_request_audio_focus = true
Fix

Replace the enable and priority calls with a check of cmd overlay list com.android.bluetooth for [x] com.carivi.bt.overlay, and log a warning only if it is missing.

F6The app's root shell is never granted

The dashboard shows root=false. The app asks for root through libsu at controller start, from a background process at boot, and nothing grants it, so Activate stack and Diagnostics do nothing. It is not blocking, because service.sh already does the same work as root.

Fix

Drop libsu and SystemBootstrap (service.sh covers it). If you keep them, request root only when the user taps a button, and document granting the app in Magisk's Superuser list.

Needs your firmware insight blocker found

Q1The tablet cannot send AVRCP commands to the iPhone

The dashboard Play button and cmd media_session dispatch play both reach com.android.bluetooth/BluetoothMediaBrowserService (it becomes the media button session), but no passthrough goes out and nothing starts on the phone. The session has been in an error state since boot, while both state machines report Connected:

A2DPSinkStateMachine state=Connected
AvrcpControllerStateMachine state=Connected
BluetoothMediaBrowserService  active=true
  PlaybackState {state=7, ... error=Bluetooth audio disconnected}   (updated 25 s after boot)
MediaSessionService: Sending KeyEvent { KEYCODE_MEDIA_PLAY } ...    (no AVRCP traffic follows)
bt_btif : bta_av_co_get_active_peer: peer index out of bounds: 5

Effect: NowPlayingController.prepare()/play() are no-ops, so Mode 1's fallback focus path and the Now Playing bar do nothing. The auto-focus overlay may still cover Mode 1 when the phone starts playback itself.

Likely origin: dual mode from btdual_patch v5 rather than your module. When v5 was first verified, iPhone absolute volume had also stopped driving the tablet, which points to the same missing active device. We have not yet A/B-tested with carrelay_ivi removed.

Question

On this QTI R stack, how should the sink-side peer become the active one in bta_av_co and AvrcpControllerService, so that the media session leaves the error state and transport commands are sent?

Q2Open risk under all three modes: source and sink at the same time

Modes 1, 2 and 3 all assume the native stack can hold the car link (tablet as source) and the iPhone link (tablet as sink) at once. Our 2026-11-03 disassembly of libbluetooth_qti.so on this build found:

  • One btif_av instance pool shared by both roles, sized in init_src by maxconnectedaudiodevices (global at 0x3dbf30).
  • BTA_AV_REGISTER_EVT assigns handles to indices in arrival order, with no role.
  • connect_int takes the first IDLE index regardless of UUID.
  • bta_av_co assumes a single active peer.

btdual_patch v5 works around the second and third points: the sink worker starts, the 3 s suspend is removed, and the source registration also creates the SNK SEPs (codecs 7 to 9, tsep 1, bte_av_sink_media_callback and bta_av_sink_data_cback). With it, phone-to-tablet music decodes in dual mode, confirmed by ear. The car link at the same time has not been tested yet; that is our next test. If it fails, it fails below all three modes, and the fix belongs in the native stack, not in routing.

Small items minor

M1LOCKED_BOOT_COMPLETED never reaches the receiver

The app is not directBootAware, so that action is never delivered. Mark the receiver direct-boot aware or drop the action.

M2media3-ui is declared but unused

Nothing imports it. Removing it shrinks the APK; we dropped it in the test build.

M3Build prerequisites

Add to the README: NDK 26.3.11579264 and CMake 3.22.1 are required. platforms/android-30 is optional, since the RRO links fine against android-34. We built with Gradle 8.10.2 instead of the bundled wrapper.
