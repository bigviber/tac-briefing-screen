## Roadblocks / feedback so far
R1. **service.sh restarts Bluetooth on the first boot.** `pm enable .avrcpcontroller.AvrcpControllerService` and `pm disable .avrcp.AvrcpTargetService` change component state for the first time; PackageManager then kills the owner app: `ActivityManager: Killing com.android.bluetooth/1002: change com.android.bluetooth` at boot+12 s (3 'Scheduling restart of crashed service' lines). Later boots are clean (state already set). Suggestion: only call `pm enable/disable` when the state differs (check `pm dump`/`dumpsys package` first), or do it once in customize.sh, and document the one-time restart.

R2. **`android:persistent="true"` on the priv-app is risky on this tablet.** A persistent system app that crashes at boot loops into recovery (this exact failure class happened 2026-11-02 with Lenovo's persistent tbengine). Test build uses `persistent="false"`; service.sh + the boot receiver still start the relay service. Suggestion: drop persistent.

R3. **The tablet cannot start/stop iPhone playback (blocks Mode 1's MediaSession hook).** Dashboard Play and `cmd media_session dispatch play` both reach `com.android.bluetooth/BluetoothMediaBrowserService` (it becomes the media button session), but no AVRCP passthrough goes out. The session has been `PlaybackState state=7 error="Bluetooth audio disconnected"` since boot, while A2DPSinkStateMachine and AvrcpControllerStateMachine are both `Connected`. bt_btif: `bta_av_co_get_active_peer: peer index out of bounds: 5` (no active sink peer). So `NowPlayingController.prepare()/play()` (FocusRoutingEngine's fallback focus path) does nothing. Probably pre-existing with btdual_patch v5 (2026-11-03 v5 note: iPhone absolute volume stopped driving the tablet in dual mode = same 'no active AVRCP device' symptom); NOT yet A/B-tested without carrelay_ivi. Ask: how should the sink-side active device be set on this QTI R stack (A2dpSinkService/AvrcpControllerService setActiveDevice equivalent) so the session leaves the error state?

R4. **App asks for root through libsu but nothing grants it.** Dashboard shows `root=false` (Magisk superuser prompt at boot with nobody to answer). Activate stack / Diagnostics buttons do nothing. Not blocking (service.sh does the root work). Suggestion: document granting Magisk superuser to com.carivi.relay, or drop libsu and rely on service.sh.

R5. **`cmd overlay enable` on static overlays logs a misleading failure.** service.sh logs `com.local.btsink.overlay not present (ok)` and `com.carivi.bt.overlay enable failed/not present`, yet both are enabled ([x]) and the lookup shows the new values. Static overlays cannot be toggled; suggestion: check `cmd overlay list` instead.

Why it failed at 01:45 is unknown: last night's capture has no onPlay line at all and the same 0xFE.
- active=true is explained by the stream starting, not a cause: requestMediaKeyFocus runs at each start and the session goes active right after onPlay.
- **Pause does not work from the tablet.** Media-key PAUSE reaches the session and is dropped (actions=0). Car Home's button keeps showing Play because the session never reports playing. Only the iPhone or a dropped link stops the music.
- **R6 (new): no track info, no play state, no library, in dual role.** Session stays state 7, metadata null; Car Home shows "Nothing playing" during real playback and "does not share its library". Two causes in libbluetooth_qti.so (v5 and stock have the same code here):
  - R6a. `p_bta_av_cfg` (0x3def20, .bss) is one global written only in bta_av_api_register at 0x1288a4 by service UUID: 0x110B -> sink table 0x3d22f0 (company_id 0x001958 AVRC_CO_METADATA), 0x110A -> source table 0x3d2260 (company_id 0xDAA119 AVRC_CO_GOOGLE). BTA_AvVendorCmd reads company_id through it (0x126eb0). On the wire the tablet's CT GetCapabilities carries `da a1 19` (q2_avctp_frames.txt), so the source table is in effect; the iPhone answers REJECTED, status 03, about 50-80 ms later. The tables also differ at +8: CT/TG categories, sink c1 03 / 02 00, source 02 00 / d1 00, and at +0x20, 01 vs 07. bta_av_rc_create (0x11f264) and bta_av_conn_chg also read this pointer.
  - R6b. btif_rc_handler BTA_AV_META_MSG_EVT (0x20cdc0): `ldr x8,[0x4003e8]; cbz x8,0x20cfe4` tests the target callbacks first and tail-calls handle_rc_metamsg_cmd (0x209d20). The controller branch (0x20cfe4, handle_avk_rc_metamsg_rsp 0x20d1d0 / _cmd 0x20dbec) only runs when target callbacks are NULL. BluetoothAvrcpServiceJni logs the RC connect, so the target side is up and every vendor reply goes to it (`avrc_pars_vendor_cmd: length is incorrect, status: 3`, `avrc_pars_vendor_rsp: invalid parameter length 0`). The controller's request therefore times out: `handle_get_capability_response: Error capability response: 0xFE` exactly 2 s after connect, on every connection, last night too. Reading 0xFE as the btif_rc status-command timeout value is from memory of AOSP; the 2 s timing fits. No retry, no event registration afterwards (no notification traffic in the frames).
  - Passthrough is unaffected: it has its own event (BTA_AV_REMOTE_RSP_EVT), which is why Play and Next work.
  - Fixing only one of R6a/R6b is not enough. Untested inference: both follow from the source/target role being up, and the 2026-11-03 receive-only notes record the library working.
